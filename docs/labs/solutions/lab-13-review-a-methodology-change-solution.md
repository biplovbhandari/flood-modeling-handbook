The proposal excludes no product or reach class even though its supplied evidence contains only two synthetic symptoms and a proposed three-reach study.
The evidence scope is therefore smaller than the requested rollout scope.

The verdict is `NOT READY` because several prerequisites cannot be safely deferred as rollout conditions:

- the selected threshold remains \(10^{-3}\) rather than the synthetic \(5 \times 10^{-4}\);

- limited ND `existing_scenarios` adoption can directly admit old-tolerance manifests without comparing tolerance, run settings, boundaries, hot start, or asset existence;

## 4. Identity, compatibility, reuse, and provenance analysis

### 4.1 Schema acceptance is not scientific backward compatibility

**Current implementation:** The public schemas already accept a different tolerance.
That fact means a caller can request a different value under the reviewed code.

It does not prove backward compatibility.
The threshold can change termination time and therefore final depth, WSE, extent, STL, hot-start state, adaptive response metrics, selected library behavior, upstream transfer, and composite products.
Consumers that parse the same manifest can still receive scientifically different content.

### 4.2 Exact target reuse at the predicted address

**Current implementation:** Exact reuse compares complete stored `RunScenarioInputs` with the new request.
An old manifest containing \(10^{-3}\) is unequal to an otherwise equal request containing \(5 \times 10^{-4}\).
The function therefore does not return that old manifest as an exact reuse.

The address was derived before this equality check and does not contain the tolerance.
The new solver request therefore retains the same destination.

### 4.3 Limited ND caller-supplied adoption

**Current implementation:** Before the adaptive ND loop requests exact target scenarios, `_adopt_existing` reads the caller-supplied `existing_scenarios` manifests.
It admits a schema-valid manifest when reach ID, full model ID, current run identity hash, and discharge inside the inclusive requested range match.
It does not compare the stored convergence tolerance, run configuration, downstream boundary geometry or slope, hot start, output interval, wall-time setting, termination reason, or referenced-asset existence with current intent.

An old-tolerance manifest can therefore enter the new-tolerance `done` set directly without reaching the complete-input equality check.
If it is at minimum discharge, it becomes the initial reference.
Other adopted discharges contribute response metrics to proposal curves and can be selected as an already-simulated trial for re-judgment.
An accepted adopted scenario can advance the reference, while an adopted search position can become the current position.
The current position's depth asset can then be named as the hot start for a newly simulated scenario.
These paths can influence adaptive membership reasoning even though the current job lacks a durable explicit selected-member list.

**Inference from current implementation:** The old-tolerance manifest can therefore influence a new-tolerance library more directly than the same-address exact-reuse risk.
It can be reused as algorithm state without rerunning and without proving asset existence or scientific compatibility.
The packet does not establish that this occurred operationally, and it does not authorize treating the two tolerances as compatible.

### 4.4 Exact inequality and collision can coexist

**Inference from current implementation:** Because unequal complete inputs reject reuse while the address omits the unequal field, the new request can execute and publish to the same final addresses.
Sequential copying can replace some old assets before failure and leave others from the old generation.
If all writes succeed, the older generation can still be lost in place.

This is a design-risk inference.
The packet contains no operational storage history proving that an overwrite has occurred.

### 4.5 Identity and generation fields

The review should consider these fields for a collision-safe run generation:

- authorized methodology revision;
- convergence metric definition and tolerance;
- save interval and other settings that change the metric or stopping state;
- solver name, executable version or build, and image digest;
- model realization and source data identities;
- boundary construction and values at sufficient precision;
- hot-start source identity;
- wet-dry and other solver options that affect state; and
- any hardware or numerical environment detail shown to affect reproducibility.

Not every field must occupy one flat hash.
The contract must nevertheless ensure that every scientifically invalidating difference creates another immutable generation or is governed by a proven compatibility relation.

### 4.6 Consumer compatibility

No old and new consumer pairing is established as safe by the packet.
Compatibility would require evidence that each consumer:

- reads the new manifest and identity version;
- applies complete equality or an authorized compatibility predicate to caller-supplied ND manifests before they enter adaptive state;
- refuses incompatible or mixed methodology generations;
- receives all required assets and datums;
- preserves selected membership and dependency generation;
- interprets convergence evidence correctly;
- can distinguish experimental from accepted outputs; and
- has validation evidence for the intended use of new outputs.

An old consumer can remain compatible only if its accepted scientific meaning and required provenance are unchanged or an authorized compatibility layer supplies the missing guarantees.

### 4.7 Idempotent retry and adoption

Before returning or adopting an existing generation, the job and caller contract must observe:

1. The complete stable request identity.
2. The expected immutable generation address.
3. A schema-valid manifest with equal or explicitly compatible inputs.
4. Every required asset at that generation.
5. Matching content checksums and expected dimensions or geometry.
6. One-generation consistency with no staging residue exposed.
7. Applicable selected-membership and acceptance state for the consumer.
8. Complete scientific compatibility with current tolerance, run settings, boundary, hot start, and intended adaptive role.

A retry after partial publication should continue or replace only isolated staging content.
It should not write into a visible accepted generation.
The controller must not pass an old-tolerance manifest through `existing_scenarios` for new-tolerance intent unless an authorized compatibility rule and asset observation show that reuse is valid.

## 5. Validation and sensitivity plan

### 5.1 Defects in the supplied plan

The three convenient reaches do not establish representative coverage.
Maximum depth and runtime omit local WSE, extent, flux, full balance, edge behavior, STL, stage-transfer consequences, and composite effects.
The study does not control save interval even though the metric compares consecutive saved outputs.
It does not assess interactions with downstream control, domain, terrain, topobathymetry, roughness, grid resolution, inflow placement, wet-dry behavior, hot starts, or solver build.

The same data cannot both choose a pass limit and independently demonstrate passing performance without a justified validation design.
The reviewer-chosen synthetic limits also lack authorized acceptance authority and uncertainty treatment.

A tighter threshold can increase runtime without removing a local transient.
It can also change the saved state used for STL, hot start, and adaptive response.
Its direction of benefit is therefore an Open question rather than an automatic improvement.

### 5.2 Minimum defensible program

#### Intended-use specification

Define the ND, KWSE, transfer, and composite decisions supported by the change.
State excluded quantities and uses.
Predeclare acceptance criteria, uncertainty allowances, permitted restrictions, and the authorized acceptance authority before viewing final results.

#### Representative design

Stratify cases across material reach lengths, slopes, confinement, floodplain storage, downstream controls, domain-edge proximity, confluences, structures, data quality, terrain and bathymetry limitations, boundary families, flow and stage ranges, and scenario positions.
Record source and method revisions for every case.

#### Verification evidence

Verify the implemented threshold, strict comparison, save interval, persisted diagnostics, simultaneous edge behavior, identity movement, address derivation, exact target reuse, limited ND caller-supplied adoption, publication states, retry, materialization, and consumer compatibility.
Use controlled analytical, conservation, regression, and failure-path tests where applicable.

#### Numerical evidence

Retain time histories for local WSE, depth, extent, velocity or flux where relevant, domain storage, inflow, outflow, sources and sinks, full-balance residual, edge state, and termination conditions.
Compare space and time resolution or otherwise estimate numerical error for the decision-relevant quantities.

#### Initial-condition evidence

Compare cold starts or scientifically compatible alternative hot starts where the result may depend on the supplied depth-only seed.
Require local state and decision metrics to agree under predeclared criteria rather than assuming final independence.

#### Sensitivity sequence

Begin with downstream condition and domain because they can change hydraulic control and edge behavior.
Then assess terrain and topobathymetry, roughness and resolution, inflow distribution, wet-dry settings, and convergence controls.
Test interactions among threshold, save interval, hot start, domain, boundary, and grid where one-factor-at-a-time results could mislead.

#### Validation or benchmark evidence

Use independent observations of WSE, stage, extent, depth, or another intended-use quantity when available.
When using a model benchmark, match source data, forcing, terrain processing, roughness, boundaries, grid, initial state, solver build, and comparison time, and preserve the benchmark's own uncertainty and scope.
Keep calibration or threshold-tuning cases separate from independent assessment, or justify a cross-validation design.

#### Operational and artifact evidence

Verify collision-safe identities, immutable generations, atomic promotion, retries, complete manifests, every required asset and checksum, materialization retraction on deletion or mismatch, selected membership, transfer bindings, composite provenance, monitoring, and rollback.

#### Evidence retention

Retain failed, ambiguous, and out-of-scope outcomes.
Do not tune away an unexpected result without recording the competing hypotheses and follow-up evidence.

### 5.3 Acceptance boundary

No universal numeric pass threshold can be derived from the supplied packet.
The authorized acceptance authority must define decision-specific criteria after the validation design and uncertainty model are established and before the final evidence is judged.

## 6. Rollout, migration, monitoring, and rollback plan

2. Approve or reject the new methodology through the authoritative decision process.
3. Version the public input, identity, manifest, evidence, and acceptance contracts.
4. Record which old and new combinations are compatible.

### 6.2 Collision-safe implementation

5. Add the changed method to a content-complete run generation identity or another immutable generation mechanism.
6. Update address prediction in both producer and observer.
7. Update manifest provenance and retained convergence evidence.
8. Update all planners, `existing_scenarios` construction, cache lookups, selected memberships, transfer bindings, composite manifests, exports, and monitoring consumers.

### 6.3 Read-only inventory

9. Inventory every affected model, ND scenario, KWSE scenario, caller-supplied `existing_scenarios` entry, selected member, downstream source, upstream dependency, composite, export, acceptance record, and retained generation without changing them.
10. Classify each object by recorded convergence tolerance and evidence as compatible, requiring revalidation, requiring recomputation, or excluded.

### 6.4 Bounded evidence rollout

11. Produce shadow generations under new addresses for the representative validation set.
12. Prevent those generations from entering selected libraries, serving as stage-transfer sources, or contributing to production composites before acceptance.
13. Compare old and new generations under predeclared criteria and retain all outcomes.

### 6.5 Atomic publication and idempotent retry

14. Write each complete generation to isolated staging.
15. Verify assets, checksums, schemas, identities, and compatibility.
16. Promote atomically or atomically change a pointer to the immutable generation.
17. Make equivalent exact retries return the same verified generation, make unequal requests create another generation, and prevent limited ND adoption from bypassing that distinction.

### 6.6 Materialization and promotion

18. Require independent observation of every required asset, checksum, identity, and generation before recording materialization.
19. Require the authorized acceptance record before the generation becomes eligible for the stated scientific use.
20. Promote through bounded stages with explicit entry criteria, exit criteria, stop triggers, and owner approval.

### 6.7 Migration

21. Recompute or revalidate the complete affected inventory according to the approved classification.
22. Exclude old-tolerance manifests from new-tolerance `existing_scenarios` inputs unless the authorized compatibility and asset-observation contract explicitly admits them.
23. Move selected memberships and transfer dependencies only when their complete compatible generation set is materialized and accepted.
24. Regenerate composite products with a source manifest that pins every contributor.
25. Reconcile migration progress against the original inventory and investigate every missing or extra object.

### 6.8 Monitoring

26. Monitor method revision, producer build, threshold, termination distribution, both reuse branches, full-balance and local-state evidence, edge results, runtime, failures, identity collisions, partial publication, checksum mismatch, materialization retraction, selected membership, transfer dependency, and product shifts.
27. Alert named owners on threshold excursion, limited-adoption mismatch, missing evidence, incompatible generation, or validation drift.

### 6.9 Rollback

28. Halt new promotion at the first predeclared stop condition.
29. Restore the prior authorized decision and compatible producer and controller versions.
30. Restore the prior `existing_scenarios` construction and compatibility rules together with selected memberships, transfer bindings, composite pointers, and consumers to retained prior generations.
31. Re-observe prior assets and checksums before declaring rollback materialized.
32. Confirm the prior acceptance scope still applies and record the incident, affected products, and required reassessment.

Restoring only `volume_convergence_tolerance=0.001` is insufficient when prior artifacts were overwritten, limited adoption admitted incompatible state, memberships moved, or consumers changed.
